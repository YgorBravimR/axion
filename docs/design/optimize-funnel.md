## Problem Statement

Axion's OPTIMIZE today is a one-shot grid: pick params, set ranges, run sweep,
compare. There is **no guided journey** from "I have no idea which knobs
matter" → "I have a frozen `hawks_v0_tuned` preset with full provenance and
auditability." Users (today: Ygor as sole operator; tomorrow: anyone using
Axion to tune a strategy) must manually:

1. Run a broad sweep, eyeball results.
2. Manually narrow ranges around a winner.
3. Re-run, hope it's better.
4. Repeat with no breadcrumbs.

The Phase 1 trilogy (provenance, walk-forward OOS, Pareto frontier) is shipped.
The Phase 2 builder system (`StrategySweepBuilder` for Hawks + ORB) is shipped.
What's missing is the **meta-flow** that organizes multiple sweep runs into
one coherent "hero hunt" journey.

## What Makes This Cool — the GA framing

The mental model is a **genetic algorithm** (Ygor's framing, captured
verbatim): "Take a _range_ of good DNAs from the first run, breed them into
a deeper check, iterate."

- **Broad stage** = wide population sample (cardinality-capped low; enums + big ranges).
- **Refine stage** = explore the **neighborhood union** of the surviving population.
- **Freeze stage** = N=1, the fittest offspring promoted to a shadow preset.

The Pareto frontier (Phase 1c, shipped) is **already the survivor-selection
UI** — multi-select K points on the frontier and click "Breed these K." Each
refined offspring carries a `parentRunIds: string[]` array, so lineage is
traceable forever via the existing provenance system.

## Pareto Selection Principle (Ygor's stated rule)

> "Every losing money setup is cut. Every profit maker can go forward. The
> user may value Assertivity for mentality, but we always recommend
> PROFIT FIRST — money in pocket on top of any other parameter."

This becomes 4 hard rules in the design:

1. **Survival cut (structural)**: any run with `summary.profitFactor < 1` is
   excluded from the breeding pool entirely. Not dimmed — removed. Frontier
   computation runs only on profit-positive survivors.
2. **Configurable axes**: user picks any 2 metrics from a known set as the
   frontier objective.
3. **Opinionated default**: the recommended frontier is
   `(profitFactor desc, maxDrawdown asc)` — profit first. UI always shows
   "Recommended" badge on this default.
4. **Soft override**: user can pick `(assertivity, drawdown)` or other
   combinations for psychological comfort, but the recommended config stays
   visually distinct.

Glossary (Ygor's vocabulary, used throughout):

- **Assertivity** = win rate (% trades that closed profitable).
- **DNA / genome** = a `StrategyRecipe` instance (one combination of leaf values).
- **Hero-win** = a frozen offspring meeting `PF ≥ X AND OOS robust AND
matchRate ≥ Y AND trades ≥ N AND user-confirmed`.

## Constraints

- Must not break the shipped legacy flow (Hawks/ORB selecting via inline
  sweep builder works as-is when the funnel is not invoked).
- All persistence on top of the shipped `OptimizationRunProvenance` schema
  (extend with `parentRunIds`, `stage`, `journeyId`; everything else reuses
  what's there).
- No new server-side dependency; localStorage continues to be the run store.
- `pnpm lint`, `pnpm lint:strict`, i18n parity must stay green.

## Premises (agreed by Ygor in `/office-hours` D1)

1. ✅ Three discrete stages (broad / refine / freeze) is the right abstraction.
2. ✅ Stage is a property of the **run**, not a separate Journey object. Lineage
   is conveyed via `parentRunIds[]` on each run.
3. ✅ "Refine from selected" opens the sweep-config editor pre-populated with
   the **union of K parents' values + ±1 step suggestions**. User edits a
   delta from the population.
4. ✅ Frozen hero-wins **shadow** the source preset (e.g.,
   `hawks_v0_tuned_2026-05-30`). The dropdown will accumulate; a future
   "promote to canonical" path is deferred to backlog.
5. ✅ Provenance-as-artifact: a frozen preset IS the localStorage entry plus
   its `provenance`. No new export format.
6. ✅ MAX_COMBINATIONS is stage-aware: broad=500, refine=3000, freeze=1.
   Starting numbers, NOT benchmarked — the existing P3 backlog entry
   "benchmark MAX_COMBINATIONS cap" picks up empirical work later.

## Approaches Considered

### Approach A: GA-style multi-parent funnel (CHOSEN)

K survivors from the Pareto frontier breed into a refine population. Refine
explores the union of K parents' neighborhoods. Freeze picks one offspring
and promotes to a shadow preset.

**Effort**: M (human: ~3-4 days / CC+gstack: ~1-2 focused sessions)
**Risk**: Low-Med — K-parent neighborhood union is the only non-trivial new code.

**Reuses**:

- `StrategySweepBuilder` (shipped): leaves get pre-populated from K parents.
- `ParetoScatter` (shipped, needs upgrades — see "Pareto upgrades" below).
- `OptimizationRunProvenance` (shipped): extend with 3 fields.
- `recipeFromCombo` (shipped): combo → recipe synthesis is reused.

### Approach B: Single-parent narrow-refine (REJECTED)

Cheapest (S effort), but doesn't match the GA mental model. Single-parent
ignores Pareto's whole point — the frontier IS the survivor set, not a
podium with one winner.

### Approach C: Free-form with stage tags (REJECTED)

Minimal (XS), no funnel mechanics — just labels. Defers the actual journey
work; retires the backlog entry as "not pursuing" rather than "shipped."

## Recommended Approach (A) — full architecture

### Data model extensions

```ts
// Extend src/types/backtest.ts

interface OptimizationRunProvenance {
	// ...existing fields (sweepId, datasetHash, candleCount, etc.)...
	/** Stage in the hero-hunt funnel. Undefined for legacy runs + ad-hoc sweeps. */
	stage?: "broad" | "refine" | "freeze"
	/** Parent runs whose Pareto-frontier selection produced this run's recipe.
      Empty for broad runs (no parents); length≥1 for refine; length=1 for freeze. */
	parentRunIds?: string[]
	/** Journey grouping. All runs in one hero-hunt share a journeyId.
      Generated at broad-stage start; carried forward through refine/freeze. */
	journeyId?: string
}

interface HeroWinPreset {
	presetId: string // e.g. "hawks_v0_tuned_2026-05-30"
	sourcePresetId: string // e.g. "hawks_v0"
	recipe: StrategyRecipe
	frozenAt: string // ISO timestamp
	journeyId: string
	// Hero-win qualifying metrics at freeze time:
	metrics: {
		profitFactor: number
		profitFactorOOS?: number
		matchRate?: number
		trades: number
		oosRobust: boolean
	}
	notes?: string // user-supplied
}
```

Stored alongside runs in localStorage under `axion:optimize:heroPresets`.

### Pareto upgrades (gating Phase 1 of the funnel)

Per Ygor's D3 answer ("All of the above, plus configurable axes for known
parameters"), every gap below ships in Phase 1:

**GAP 1+5 — Configurable axes + Top-N pool**:

- New `ParetoConfig`: `{ xAxis: MetricKey, yAxis: MetricKey, mode: "frontier" | "top-n", topN?: number }`.
- `MetricKey` is a union of known axes:
  `profitFactor`, `maxDrawdown`, `numTrades`, `assertivity` (=winRate),
  `avgR`, `matchRate`, `profitFactorOOS`, `maxDrawdownOOS`.
- UI: two `<select>` dropdowns above the scatter. Default
  `(profitFactor, maxDrawdown)` carries a "Recommended — profit first" badge.
- `pareto.ts` becomes generic over axes via a `metricExtractor(run, key) => number` function.

**GAP 2 — Multi-select for breeding**:

- Each Pareto point becomes a clickable + checkbox-bearing node.
- Selected points outlined in accent color + checkbox state in chart state.
- "Breed selected (K=N)" CTA appears in the scatter panel when ≥1 point selected.
- Default: when scatter first renders, frontier points are pre-checked.

**GAP 3 — IS-vs-OOS frontier toggle**:

- New radio: `Frontier metric source: IS | OOS | Combined`.
- Defaults to OOS when walk-forward was enabled on the source sweep.
- Combined mode = harmonic mean of IS + OOS (later phase; ship IS/OOS first).

**GAP 4 — Constraint filter chips**:

- Chips: `trades ≥ 30`, `matchRate ≥ 0.5`, `OOS robust only`, `profit only`.
- `profit only` is **on by default and not togglable** (enforces the survival
  cut from Ygor's principle — PF<1 runs are structurally excluded).
- Other chips are sticky per-session and don't reset on re-render.

### Loser Pattern Mining (negative selection)

Ygor's addition (D4): finding the fittest isn't enough. We also need to know
**what patterns drive the losers, the bigger drawdowns, and the win-rate
collapse.** Pattern mining surfaces _causal_ leaves (those that flip outcomes)
vs _correlated_ leaves (those that just happen to co-occur with winners).

This is **post-broad-sweep analysis**, before Pareto multi-select. Two
companion views:

**A. Loser frontier** (mirror of the winner Pareto):

- Same scatter component, but axes inverted: worst PF × worst drawdown.
- Same multi-select UI — user can pick the worst N losers and ask "what do
  these have in common?"
- Survival cut **inverts**: only loss-makers (PF < 1) shown.

**B. Pattern Inspector** (per-leaf concentration):

- Extends the existing `ParameterHeatmap` component (Phase 1c, shipped).
- New mode toggle: `Winner concentration | Loser concentration | Delta`.
- `Delta` mode is the gold: shows `(loser_freq − winner_freq) / overall_freq`
  for each leaf value. Strongly positive cells = leaf values that
  disproportionately appear in losers. Strongly negative = appear in winners.
- Threshold to define "loser" / "winner" is configurable (default: bottom-20%
  for losers, frontier for winners).

**Output to the user**: a ranked list of "drivers" surfaced under the broad
scatter:

- "**Top causal leaves** (high winner-vs-loser delta):
  `aggressionMode=reversed` appears in 67% of winners vs 12% of losers.
  Recommend FIXING this in refine."
- "**Drawdown drivers**: `breakeven.enabled=false` correlates with
  drawdowns -15% worse than baseline."
- "**Win-rate killers**: `wave1MinBricks ≤ 3` drops assertivity from 64% to
  42% across the broad sweep."

This drives refine-stage decision-making — instead of just "narrow around
the K parents," the user gets actionable advice: "lock these leaves to
winner-favored values; only sweep where the delta is small (uncertain)."

### Runs comparison table changes

- New columns: `Stage`, `Parents`, `Journey`.
- `Stage` shows badge: broad/refine/freeze.
- `Parents` shows count + tooltip with parent run labels.
- `Journey` shows short journeyId or "ad-hoc" for non-funnel runs.
- New filter chip: "This journey only" — limits to current `journeyId`.

### Hero-win freeze flow

1. User clicks a refine run that looks ready.
2. "Freeze as hero preset" CTA appears in the run detail panel.
3. Modal opens — validates hero-win gates:
   - `PF ≥ 1.5` (configurable threshold, default per backlog)
   - `OOS robust = true` (when walk-forward was active)
   - `trades ≥ 30`
   - User confirms suggested preset ID + adds optional notes.
4. On freeze:
   - New `HeroWinPreset` written to `axion:optimize:heroPresets`.
   - Preset registered in `ALL_PRESETS` (`hawksPresets.tuned` array) and
     appears in the strategy dropdown on next render.
   - Source recipe's `provenance.stage = "freeze"`.
   - `journeyId` recorded as completed in journey timeline.

### Stage-aware cardinality caps

Per Ygor's D2 answer (Approach A with stage-aware caps):

| Stage  | Cap  | Rationale                                                                              |
| ------ | ---- | -------------------------------------------------------------------------------------- |
| Broad  | 500  | Breadth-first; enums + wide ranges dominate. Avoids cognitive overload on first sweep. |
| Refine | 3000 | K parents × tight neighborhoods compound. Need depth without runaway.                  |
| Freeze | 1    | Snapshot only — no sweep.                                                              |

These are starting values. The P3 backlog entry "benchmark
MAX_COMBINATIONS cap" picks up the empirical work; stage-aware caps will be
re-tuned then.

## Open Questions

1. **K-parent neighborhood union — numeric collapse rule**: if 3 parents have
   values `{20, 25, 30}` for a numeric leaf, do we sweep
   `[15..35, step 5]` (smooth range) or `[20, 25, 30]` (exact set)?
   Range is more genetic-algorithm-like (allows crossover into unseen values);
   set is more conservative. **Recommend: smooth range with step = min(parent
   value step, leaf.defaultStep).** Surface to `/plan-eng-review`.
2. **Refine of a refine**: when user breeds from a refine-stage Pareto, the
   new run's `parentRunIds[]` references refine runs which have their own
   parents. Should the lineage be flattened (`parentRunIds = root parents`)
   or kept nested (each refine has only its direct parents)? **Recommend:
   nested — keeps the journey auditable.**
3. **Journey abandonment**: what UX when a journey produces no hero-win after
   N refines? Need a "Mark journey closed without hero" action so the
   timeline isn't polluted with abandoned half-finished hunts. Deferred to
   backlog as P3 ("Hero hunt journey timeline UX").
4. **Hero-win threshold configurability**: today the gate is `PF ≥ 1.5 AND
OOS robust AND trades ≥ 30`. Should these thresholds live in a settings
   panel, or hard-coded in code? **Recommend: hard-coded in
   `src/lib/optimize/hero-win-rules.ts` with constants exported; settings
   panel as P3 follow-up.**

## Success Criteria

- A broad sweep on Hawks (~500 combos) completes in ≤2 minutes.
- User can multi-select 3 Pareto points, click "Breed selected," and see a
  refine config pre-populated with the union of 3 parents' values in ≤500ms.
- A refine sweep on Hawks (~3000 combos) completes in ≤6 minutes.
- A frozen hero preset appears in the strategy dropdown immediately and is
  selectable as a recipe for a fresh ad-hoc backtest.
- Re-running the same recipe at a frozen preset on the same candle dataset
  produces identical hashes (provenance reproducibility — verified in Phase 1b).
- `pnpm lint` + `pnpm lint:strict` + i18n parity stay at 0 errors.

## Distribution Plan

- **Consumed in-process**: hero-win presets persist in localStorage, appear
  in the strategy dropdown, are immediately selectable. No build/release step
  per preset.
- **Cross-machine portability**: per Ygor's D1 (premise 5), provenance-as-artifact.
  A user on a different machine restores by importing the localStorage entry.
  A future "shareable preset URL" path is deferred to backlog if needed.
- **Engine version coupling**: each `HeroWinPreset` records `engineVersion`
  via provenance. When the engine version changes (recipeHash → different
  outcome), the preset surfaces a stale-warning chip in the dropdown.

## Engineering Review (locked in 2026-05-30 via `/plan-eng-review`)

### Office-hours decisions, engineering-validated

- **Q1 K-parent numeric collapse** = smooth range; `step = min(parent value step, leaf.defaultStep)`. `expandRange()` (`src/lib/optimize/sweep-leaf.ts:120`) is float-safe and supports this directly.
- **Q2 Refine-of-refine lineage** = nested. `parentRunIds: string[]` per run; lineage walk is a graph traversal — flatten loses generation info.
- **Q3 Hero-win thresholds** = code constants in `src/lib/optimize/hero-win-rules.ts`. Settings panel deferred to P3.
- **Q4 Journey abandonment UX** = deferred to backlog as P3. Architecturally invisible (just a metadata flag).

### New decisions from architecture pass

- **journeyId timing** = lazy. Broad runs ship with `stage="broad"` and NO `journeyId`. The `journeyId` is minted when the user clicks "Breed selected" on the Pareto scatter; the resulting refine run owns it and back-fills it onto its parent broad run(s) in localStorage. Ad-hoc sweeps stay journeyId-free forever.
- **Hero preset registration** = hybrid in-memory cache + localStorage. `heroPresetsCache` hydrated from `axion:optimize:heroPresets` at app boot; freeze writes through both; dropdown reads via a hook backed by the cache. `ALL_PRESETS` and `hawksPresets.tuned` stay static and code-shipped.
- **Pareto generalization** = new `src/lib/optimize/metric-keys.ts` module exports `{ key, direction, extract, labelKey, badge? }`. `pareto.ts` becomes generic over a `MetricExtractor` function. No user input required — engineering hygiene.
- **STORAGE_VERSION_KEY bump** = bump on every shape change (even optional adds), with no-op migrations for backward-compatible adds. Unambiguous version-to-shape mapping.
- **`StrategySweepBuilder` extension** = add optional `initialSelections?: Map<path, LeafSelection>` prop. Refine stage passes the K-parent neighborhood union through this prop. No state-machine refactor.

### PR 2 perf gate

PR 2 includes a benchmark script that runs a 3000-combo Hawks refine on a fixed dataset and records wall-clock. Outcome ladder:

- **<6 min** → ship refine cap = 3000.
- **6–15 min** → ship refine cap = 3000 with WARN_COMBINATIONS = 1500.
- **>15 min** → cap drops to the largest power of 500 that fits 6 minutes. Design doc updated.

The benchmark result lands in the PR description as a perf snapshot for future regression checks.

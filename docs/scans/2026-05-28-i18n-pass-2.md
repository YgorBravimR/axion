## Root causes

### RC-1: Detector treated hook bindings as file-scoped, not function-scoped

**What**: The v1 detector built one `Map<hookVar, namespace>` per file. When the same file declared multiple components each binding `const t = useTranslations(...)` to different namespaces (a common pattern in Axion — e.g. `hawks-import-section.tsx` has 4 cards each with their own scoped `t`), the map kept only the last binding. Every `t(...)` call in the file was then resolved against that last namespace.
**When it manifests**: at scan time, on any file with ≥2 `const <sameName> = useTranslations(...)` bindings. Produces missing-key reports that look plausible (correct file, correct line) but whose composed `fullKey` belongs to the wrong namespace.
**Anti-pattern signature**: a static-analysis tool that uses file-wide name resolution for variables that JS scopes per function. Caught here by the Phase 4 verification step (`pnpm i18n:check` returning 0 after the fix, despite the v1 report claiming 35 missing keys).
**Why it slipped past initial verification**: in scan 1, the detector wasn't built yet; I authored it for scan 2 as a follow-up artifact and used its output as ground truth without cross-checking against the actual JSON. The fix-then-verify discipline (read keys back in JSON before adding) caught the lie.

## Prevention rules

- **Rule**: Static-analysis tools that walk source must scope identifier resolution to function bodies, not files. For each call site at line L, resolve the binding by walking backwards to the nearest preceding `const <name> = ...` (or equivalent).
  **Detector**: ad-hoc — review any new script under `scripts/` that maps identifiers to values. Look for a single file-wide `Map<varName, ...>` that gets overwritten by repeated `set` calls. If found, ask: does this language scope these per-function?
  **Auto-fix**: manual — refactor to a per-call backward scan, as done in `scripts/check-i18n-keys.ts` v2 (`resolveBinding` function).

- **Rule**: Detector scripts MUST be cross-validated before being trusted as CI gates. Before wiring `pnpm <detector>` into `lint:strict` or any pre-commit hook, run the detector and probe a sample of its output against the source-of-truth file (JSON keys, database state, etc.) to confirm at least 95% accuracy.
  **Detector**: manual review — when adding any new `pnpm <name>:check` script, write a Phase 4 verification step alongside it.
  **Auto-fix**: manual — covered by this scan's own discipline.

## Still armed

- **67 dynamic-key references** under patterns like `t(\`status.${variable}\`)` cannot be resolved by regex-only static analysis. Each requires knowing the type of `${variable}` at compile time. Two viable next steps:
  1. **Type-aware extension**: run a `ts-morph`-based pass that, for each dynamic call, reads the variable's TypeScript type — if it's a string-literal union, expand it and check each composed key against JSON. Estimate: ~80 lines of `ts-morph`, runs in a few seconds.
  2. **Convention-based audit**: catalogue every `t(\`namespace.${x}\`)`pattern and verify the JSON sub-tree under each`namespace.\*`covers the expected enum manually. Cheaper but rots when enums change.
Recommend (1) as`pnpm i18n:check --dynamic` in a follow-up.

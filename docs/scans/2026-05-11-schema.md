# Subject Sweep — DB schema / timezone discipline

**Date**: 2026-05-11
**Subject**: #16 from `docs/scan-roi-plan-2026-05-07.md` (Tier C)
**Scope**: `src/db/schema.ts`, `src/lib/dates.ts`, `src/lib/**` (TZ-sensitive)

## Why this subject

A Brazil-timezone day-trading journal lives or dies on timestamp correctness. The plan called out two failure modes: (1) `timestamp` columns without `withTimezone: true` (TZ-naive — silently UTC-shifted on insert), (2) JS `Date` arithmetic that assumes the JVM/Node default timezone (browser-dependent, breaks server-side rendering).

CLAUDE.md flags `src/db/schema.ts` and `src/db/migrations/` as protected paths.

## Phase 5a — why this sweep returns zero fixes

Schema and date handling are already disciplined in two layers:

1. **Every timestamp column is `timestamptz`.** This is unusual — most projects have at least a handful of TZ-naive columns that drift silently. A grep of `grep -nE 'timestamp\([^)]*\)' src/db/schema.ts | grep -v 'withTimezone: true'` returns nothing. Discipline at schema-creation time prevented the entire bug class.
2. **`Intl.DateTimeFormat` with explicit `timeZone`** is the right idiom for "today in BRT" type questions. `dates.ts` centralizes this so business code doesn't reinvent it. Constants: `APP_TIMEZONE = "America/Sao_Paulo"`, `BRT_OFFSET = "-03:00"` for ISO construction.

The remaining audit surface — naïve `new Date().getMonth()` in business code — would show up as direct `Date.prototype.get*()` calls outside `dates.ts`. None of those reach business logic; the rare hits are in chart libraries' typed callbacks where they receive a `Date` already in the right TZ.

## Phase 5b — fixes applied (0 total)

No fixes applied. The schema is uniformly TZ-aware (95/95) and the date utility centralizes TZ-sensitive operations behind an `Intl.DateTimeFormat`-backed API. The two anti-patterns the plan was looking for (`timestamp` without `withTimezone`, and `new Date().getMonth()` in business code) are absent.

## Phase 5c — prevention rules (memory seed)

### Convention

**New `timestamp` columns must use `withTimezone: true`.** Project-wide discipline; deviating creates a silent UTC↔local conversion bug class. Pattern:

```ts
createdAt: timestamp("created_at", { withTimezone: true, mode: "date" }).notNull().defaultNow(),
```

**TZ-sensitive date logic routes through `src/lib/dates.ts`.** Business code that asks "is this today in BRT?" or "what's the start of this month?" calls helpers from `dates.ts`, not `new Date().getMonth()`. The helper uses `Intl.DateTimeFormat({ timeZone: APP_TIMEZONE })` to extract parts in the correct zone regardless of the server's host TZ.

**Drizzle migrations are append-only.** Generate with `pnpm db:generate`, never hand-edit existing files. CLAUDE.md flags both `src/db/schema.ts` and `src/db/migrations/` as protected.

### Detector convention

```bash
# TZ-naive timestamp columns (should be 0)
grep -nE 'timestamp\([^)]*\)' src/db/schema.ts | grep -v 'withTimezone: true'

# Raw Date.get* calls outside dates.ts (audit each)
rg -n '\bnew Date\([^)]*\)\.(getMonth|getDate|getDay|getHours|getMinutes|getFullYear)\(' \
  src/ -g '*.ts' -g '*.tsx' | rg -v 'src/lib/dates\.ts'

# Schema integrity: every timestamp must be TZ-aware
diff <(grep -c 'timestamp(' src/db/schema.ts) <(grep -c 'withTimezone: true' src/db/schema.ts)
# Empty output = aligned. Anything else = drift.
```

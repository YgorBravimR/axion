## Why this subject

A financial app handles secrets (auth, JWT, encryption keys), user-controlled input (CSV/nota imports, trade notes), and persisted state. The plan flagged three classes: SQL injection via raw `sql\`\``, XSS via `dangerouslySetInnerHTML`or`eval`, and secret/env-var leakage to the client.

## Phase 5a — why this sweep returns zero fixes

drizzle-orm's `sql\`\``tagged template is the safe-by-default pattern: every`${interpolation}`becomes a positional bind parameter, not raw string substitution. The 16 usages in this codebase all follow the idiom (column references via`tableName.columnName`, typed literals, no user-input string concatenation). To produce a SQL-injection vulnerability with drizzle you'd have to deliberately use `sql.raw(userInput)` — 0 hits for that pattern.

The single `dangerouslySetInnerHTML` is in `brand-script.tsx`, which serializes a static constant via `JSON.stringify`. No path from user input reaches that prop. The component is currently dead code (knip flags it; see Subject #15) but even if revived would be safe.

Env-var hygiene: zero client-side `process.env.*` references means there's no accidental leakage of server secrets into the JS bundle. The few `NEXT_PUBLIC_*` reads (if any) would be intentional and public-safe.

## Phase 5c — prevention rules (memory seed)

### Convention

**drizzle `sql\`\``is safe;`sql.raw()` is a sharp knife.** Tagged-template interpolation becomes a bind parameter automatically. `sql.raw()` skips parameterization — only use it for trusted table/column identifiers from a strict whitelist, never user input.

**`dangerouslySetInnerHTML` is safe when content provably never touches user input.** Audit: walk back from the prop through every variable assignment to the source. Source must be a static literal, a static-imported constant, or a value run through a known sanitizer. If you can't trace it in 30 seconds, the prop is unsafe.

**`process.env.*` belongs in server code only.** Next.js inlines `NEXT_PUBLIC_*` vars into the client bundle at build time; everything else is server-only. Client-side `process.env.SECRET_KEY` reads will be `undefined` at runtime — silent bugs that look like config errors.

### Detectors

```bash
# Drizzle unsafe path
rg -n 'sql\.raw\(' src/ -g '*.ts'                                  # = 0 (audit each if any)

# XSS surfaces (audit each — but most are safe like brand-script)
rg -n 'dangerouslySetInnerHTML' src/ -g '*.tsx'
rg -n '\beval\(|new Function\(' src/ -g '*.ts' -g '*.tsx'           # = 0

# Server secrets reaching client
rg -n 'process\.env\.[A-Z_]+' src/components src/hooks -g '*.ts' -g '*.tsx'  # = 0
                                                                              # any hit → audit
```

# Fractal Planning Cascade — Phase 4: Cleanup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the legacy planning entities now that the fractal cascade owns the planning surface. Drop `monthlyPlans`, `weeklyTargets`, `dailyTargets`, the contract-based yearly columns (`valorPorContratoCents` + the four `exit*Pts` + the two `exit*Proportion`), and the legacy `strategies.targetRMultiple` column.

**Architecture:** Sequential drops, each preceded by reference migration. For every legacy entity we (a) migrate or delete every caller, (b) prove the entity is unreferenced, (c) drop schema + migration. Drops are NOT additive — Phase 4 is the only phase that issues `DROP COLUMN` / `DROP TABLE`. Each drop runs independently so a single failure can be reverted in isolation.

**Tech Stack:** Drizzle ORM, Vitest, Next.js 16 server actions, `psql` for manual migration application.

**Phase 3 baseline (already merged on `feat/yearly-tax-reporting`, tip `aab4962`):**
- 1121 unit tests passing, lint clean
- Feature flag `FRACTAL_PLAN_DUAL_WRITE` defaults ON; `=0` is the kill switch
- All `/plan/*` routes live; `/yearly-plan` and `/monthly` redirect to them when flag is ON
- Legacy tables (`monthlyPlans`, `weeklyTargets`, `dailyTargets`) still readable / writable but no longer the source of truth in the new UI

**Critical operational notes:**
- `bun run test:unit` is the test runner (NOT `bun test`).
- `bun run db:migrate` hangs in non-TTY. Apply each Phase 4 migration via `psql "$DATABASE_URL" -f src/db/migrations/0033_*.sql`.
- Pre-existing `YearTaxSummary` build error is unrelated — do not fix.
- Each task has its own commit. `Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>` trailer.
- **Destructive migrations.** Confirm the application has been deployed with the post-Phase-3 code BEFORE running these against production. The implementer's job here is the local migration + code change; production rollout is the operator's job.

`monthlyPlans` (legacy plural) and `monthlyPlan` (new fractal singular) have different shapes. The legacy table holds capital + tier per month; the new table holds R-cap overrides + Σ-aware target weeks. The migration strategy is:

1. Where the caller reads month-level capital/tier, switch to the cascade resolver via `resolveMonth({...})` and the `tierChangeLog` audit trail.
2. Where the caller writes month-level data (e.g., `/api/arch/monthly-plans/upsert`), redirect to the new server action `upsertMonthlyPlanV2` from `src/app/actions/fractal-plan/monthly.ts` (already exists from Phase 2 Task 10).
3. Where the legacy data was display-only (annual reports, command-center, live-status), replace with calls into `resolveMonth` or `tierChangeLog` queries.
4. Delete the entire `/api/arch/monthly-plans/*` route group — it's a legacy admin surface.

Sketch the helper if it does not yet exist:

```ts
// src/lib/fractal-plan/current-tier.ts
import { db } from "@/db/drizzle"
import { tierChangeLog } from "@/db/schema"
import { and, eq, lte, desc } from "drizzle-orm"

const getCurrentTierForAccount = async (
	accountId: string,
	asOf: Date
): Promise<string | null> => {
	const row = await db
		.select({ toTier: tierChangeLog.toTier })
		.from(tierChangeLog)
		.where(and(eq(tierChangeLog.accountId, accountId), lte(tierChangeLog.asOf, asOf)))
		.orderBy(desc(tierChangeLog.asOf))
		.limit(1)
		.then((rs) => rs[0])
	return row?.toTier ?? null
}

export { getCurrentTierForAccount }
```
